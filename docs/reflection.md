# Reflection

**1. Which source would be easiest to integrate into a future pipeline, and why?**

Out of all five sources I worked with, customers.csv stands out as the easiest to bring into a future pipeline. It's a flat, tabular file with a fixed, predictable schema, and pandas was able to read it in a single line of code without any special handling. This is very different from orders.json, which stores data in a nested structure that would need extra parsing logic before it could be flattened into rows and columns, or from the REST API, which depends on an internet connection and can fail if the endpoint is slow or temporarily down. Because customers.csv doesn't have any of these complications, and because its columns translated directly into PostgreSQL types with almost no adjustment (as I saw firsthand when building the lab.customers table in Task 3.2), it's the source I'd trust to integrate first with the least amount of extra engineering work.

**2. Which source presents the greatest schema or data-quality risk, and what evidence supports your answer?**

I'd point to the REST API as carrying the highest risk. Unlike a file sitting in a folder, an API is a live, external system that I don't control. When I inspected it in Task 2.3, it returned a list of 100 JSON records, but nothing in that response actually guarantees the field names, data types, or number of records will stay the same the next time I call it. A file's structure doesn't change unless someone manually edits it, but an API provider could push an update to their service overnight and my pipeline would have no warning. On top of that, there's the added risk of the request simply failing due to network issues, rate limiting, or downtime, which isn't a concern with a local file at all.

**3. What could go wrong if a pipeline is built before the source schema and contract are understood?**

Skipping the schema and contract step and jumping straight into building a pipeline invites exactly the kind of silent, hard to catch errors that are difficult to trace later. For example, if a column's data type is inferred automatically without checking it first, something like a customer ID with leading zeros could quietly get converted into a plain integer and lose information. Similarly, if I assume a field is always filled in when it isn't, which I actually confirmed happens with the email and signup_date columns in customers.csv since both had missing values during profiling, any downstream step that depends on that field being present could break or silently produce incomplete results. Without a written contract to compare against, there's also no early warning system: if the source's structure changes later on, the pipeline might keep running and producing output that looks fine on the surface but is actually wrong.

**4. How do Git, virtual environments, containers, and documentation improve reproducibility for a data-engineering team?**

Each of these tools solves a different piece of the "it works on my machine" problem. Git keeps a complete, shared history of every change to the code, so everyone on a team is working from the same version and can trace exactly what changed and when. Virtual environments keep each project's Python packages isolated, which stopped me from running into version conflicts between this lab's dependencies and anything else installed on my computer. Containers go a step further than virtual environments; the PostgreSQL setup I ran through Docker in this lab behaves identically no matter what operating system it's running on, which removes an entire category of "works for me but not for you" bugs tied to environment differences. Finally, documentation like the README and data contract I wrote captures the reasoning and assumptions that don't show up in the code itself, things like why a field is nullable, or what a schema evolution policy should be, so a new team member could pick up this project without needing to ask me directly.
